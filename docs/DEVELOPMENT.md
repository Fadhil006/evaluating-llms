Last checked: 2026-10-08. This reflects the current local single-user implementation; the repository's `README.md`, `plan.md`, and `docs/BUILD_STATUS.md` remain the startup and phase-status references.

## Project map

```text
backend/app/api/          FastAPI datasets, experiments, worker, results, review, exports
backend/app/models.py     SQLAlchemy records

backend/app/evaluation/   versioned deterministic scorers

datasets/                 original versioned JSONL convenience dataset
```

The API serves on localhost and uses SQLite; the worker is a separate process using the same mode-specific database. Frontend Vite proxies `/api` in development. The browser does not call model providers or receive provider keys.

## Commands

Prerequisites: Python 3.12+ and Node 24 LTS are documented targets; local verification recorded in `docs/BUILD_STATUS.md` used Python 3.14 and Node 26. SQLite is supplied with Python. From the repository root, optional `.env` setup is `cp .env.example .env`; values are server-process settings.

Backend setup/start (terminal 1):

```sh
cd backend
python -m venv .venv
.venv/bin/python -m pip install -e '.[dev]' -c requirements.lock
.venv/bin/alembic upgrade head
.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Frontend (terminal 2):

```sh
cd frontend
npm ci
npm run dev
```

Worker (terminal 3; choose the same `EXECUTION_MODE` as the API):

```sh
cd backend
EXECUTION_MODE=live .venv/bin/python -m app.worker
```

Open http://127.0.0.1:5173. Check `http://127.0.0.1:8000/api/health` and `/api/settings` for safe status. Ctrl+C stops each process. Do not start API/worker in different modes against different databases.

Checks:

```sh
# backend/
.venv/bin/alembic check
.venv/bin/python -m pytest -q
.venv/bin/ruff check app tests alembic

# frontend/
npm run typecheck
npm run build
npm run test:e2e
```

Playwright uses `/usr/bin/chromium`, isolated demo services, and a separate worker; set `PYTHON` if the backend interpreter differs. E2E is the browser workflow check, not live-provider verification. Dependencies are pinned by `backend/requirements.lock` and `frontend/package-lock.json`.

## Database and migrations

The configured defaults are `data/lab.sqlite3` for live and `data/demo.sqlite3` for demo. `DATABASE_PATH` and `DEMO_DATABASE_PATH` are resolved relative to the repository root and must differ. Database files are local state, ignored by git; do not put SQLite on a network filesystem. Migrations are explicit and are not automatically applied when the API starts.

After changing ORM schema, create/review an Alembic revision, apply it, and check model/schema agreement:

```sh
cd backend
.venv/bin/alembic revision --autogenerate -m "describe schema change"
.venv/bin/alembic upgrade head
.venv/bin/alembic check
```

Inspect autogenerated migrations before applying. For a fresh isolated migration check, set `DATABASE_PATH` (and `DEMO_DATABASE_PATH` to another path) to temporary repository-relative paths before running Alembic. Do not delete or rewrite an existing user's database to resolve migration drift.

## Worker debugging and interrupted runs

Run `python -m app.worker` in its own terminal and keep the API and worker pointed at the same mode/path. The worker polls about every two seconds while idle. Inspect worker output and the app's experiment progress/events and response/attempt status in the UI/API; never print environment settings, authorization headers, or raw credential-bearing provider exceptions. For backend diagnosis use a temporary DB and fixture mode rather than a live key. A persisted worker heartbeat and reconciliation of unknown external-key usage are not implemented; broader stress/HTTP failure verification remains open (see build status).

On process restart, completed responses are retained and are not intentionally regenerated. Expired leased work without a saved response is marked interrupted; if a request may have reached the provider, the remote outcome is uncertain. Progress may require explicit resume acknowledgement before retrying uncertain work. This cannot cancel a request already accepted remotely, guarantee exactly-once execution, or recover an unsaved provider response. Review attempt/error/unknown-outcome and consumed-attempt counts before resume. Resume rechecks route eligibility; never substitute a paid or different model automatically. A local attempt cap is not an authoritative account quota.

## Importing data

Use Datasets → import preview/save with UTF-8 CSV or JSONL. Required core fields: `id`, `task_type`, and `prompt`; optional `context`, `reference_answers`, `choices`, `scoring_config`, `tags`, `source`, and `license` are validated according to the task. CSV arrays/objects are JSON-encoded cell values. Limits are 5 MiB and 5,000 rows with bounded fields; duplicate IDs are rejected. Identical normalized content under different IDs is flagged for explicit acknowledgement. Preview and save both validate. Each saved version is immutable and carries a content hash/provenance. Missing source/license is unknown, not permission to redistribute. Never import arbitrary executable scorers or treat imported references as provider-visible prompts.

The built-in 30-item original dataset is separately installed from the UI. It is newly authored and CC0-1.0 attributed in the JSONL; that does not grant rights to user-imported data.

## SQLite backup and restore

Choose the correct live/demo database path. Backups may contain prompts, answers, imported data, provider metadata, and private review mappings; protect them as research data. Never put credentials in a database backup or academic export.

**Simplest consistent backup:** stop API and worker, then copy the database file to a protected destination. With both processes stopped, SQLite has no active WAL writes to capture. Do not copy only the `.sqlite3` main file while the application is writing in WAL mode.

**Online backup:** Python's standard-library SQLite backup API can take a consistent snapshot while the database is open:

```sh
python -c 'import sqlite3; src=sqlite3.connect("data/lab.sqlite3"); dst=sqlite3.connect("/safe/path/lab-backup.sqlite3"); src.backup(dst); dst.close(); src.close()'
```

Replace source with `data/demo.sqlite3` for demo. Ensure destination directory exists and is protected. Restore conservatively to a separate test path first:

```sh
python -c 'import sqlite3; src=sqlite3.connect("/safe/path/lab-backup.sqlite3"); dst=sqlite3.connect("data/lab-restore-test.sqlite3"); src.backup(dst); dst.close(); src.close()'
cd backend
DATABASE_PATH=data/lab-restore-test.sqlite3 .venv/bin/alembic upgrade head
DATABASE_PATH=data/lab-restore-test.sqlite3 .venv/bin/alembic check
```

Set a distinct `DEMO_DATABASE_PATH` alongside that override if needed. Start the API against the restored test path and check experiment counts, completed responses, exports, and paused/interrupted resumability before replacing any working database. Keep a pre-restore copy. No release-grade restore verification is yet claimed.

## Credentials and key boundaries

Application evaluation keys are server-only environment variables: `OPENROUTER_API_KEY` and `OPENCODE_ZEN_API_KEY`, optionally in the repository-root `.env` (ignored by git). `FREE_ONLY=true` is enforced. The UI/API exposes configured/not-configured status only. Never use `VITE_` variables, frontend code, browser storage, committed config, screenshots, logs, or exports for keys. Do not send application keys to the coding assistant. Do not read OpenCode's credential store from this application.

### Pricing evidence and free-only limitations

Live execution is fail-closed: exact named route, supported endpoint, current persisted zero-price evidence for every applicable charge, no model substitution/fallback, and revalidation before work. Missing or ambiguous price data is not zero. OpenRouter may expose documented free-request counters; if absent, quota is unknown. Credit balance is not a free-request quota. The app's local attempt counter cannot see usage by other clients of the same key. Zen's currently documented routes/pricing and promotional terms can change; model catalog presence or “free” wording alone is insufficient evidence. Zen remains blocked unless a maintained, dated, exact-ID official zero-price record covers all applicable charges. Actual availability and free eligibility require a fresh provider observation; this documentation does not claim any route is currently eligible. Consult dated provider evidence in `docs/PROVIDER_NOTES.md`.

### Offline demo mode

Stop all services before switching modes. Set `EXECUTION_MODE=demo` in API, worker, and migration process; the separate `DEMO_DATABASE_PATH` prevents live/demo data mixing. Apply migrations to that DB, restart services, refresh Models, install the original dataset, select the two `fixture/alpha-v1` and `fixture/beta-v1` synthetic routes, save and start the ten-item experiment. Backend fixture execution records synthetic provenance and performs no live catalog HTTP/model calls. The UI has a persistent demonstration banner and the browser test covers the ten-item run/results/review/reload flow. Both fixture routes emit identical synthetic strings; they only verify workflow/data plumbing, not model comparison or performance. Failure modes are covered separately by backend tests, not selectable demo scenarios.

## Docker Compose

With Docker and the Compose plugin installed, run `docker compose up --build`. A one-shot migration service precedes the API and worker, which share a named `/app/data` volume. The API is published only at `127.0.0.1:8000`; the worker has no published port. Built frontend files are served by FastAPI. `docker compose down` preserves the volume; `docker compose down -v` deletes all locally stored datasets and experiments, so back up first. Compose config/build/start, demo API/worker run, export, loopback binding, and completed results across Compose down/up were checked locally. A standard-library SQLite backup/restore test preserves a completed experiment and response; a full operator restore rehearsal remains open.

## Practical OpenCode guide (official docs checked 2026-10-08)

OpenCode is a coding assistant configuration, separate from the evaluation app. In the TUI, `/connect` configures credentials for a coding provider and stores them in `~/.local/share/opencode/auth.json` (official provider documentation). `/models` opens the configured model picker. Current selection syntax is a full `provider/model` ID: use `opencode --model provider/model`, `opencode -m provider/model`, or set the `model` key in OpenCode config, for example:

```json
{
  "$schema": "https://opencode.ai/config.json",
  "model": "opencode/gpt-6-luna"
}
```

Use `/models` to confirm IDs available to your configured coding provider; model availability and names change. OpenCode Zen setup is `/connect` → select OpenCode Zen → provide its key, then `/models`. Zen is paid per request and its current endpoints/models vary. A model/provider selected to help write or review this repository is **not** a model being evaluated by this app.

Keep the credential domains distinct:

| Purpose | Configuration / identity | Boundary |
|---|---|---|
| Coding assistant | OpenCode provider and `provider/model`, configured by `/connect`, `/models`, CLI or OpenCode config; credentials in OpenCode's own auth store | Never read `~/.local/share/opencode/auth.json` into the app, copy its contents into `.env`, or share its keys. |
| App evaluation gateways | Exact app gateway/model snapshots selected in an experiment; backend `OPENROUTER_API_KEY` / `OPENCODE_ZEN_API_KEY` environment | Server-only; app's free-only evidence and current endpoint policy independently decide eligibility. |

The strings may look related, but OpenCode's `opencode/model-id` coding route is not automatically the app's `opencode_zen` provider route, nor proof of price, quota, endpoint support, or experimental identity. Do not assume an assistant model is free or eligible for evaluation.
