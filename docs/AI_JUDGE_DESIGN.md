# Optional AI judge — proposed, not implemented

Keep the working comparison flow independent of an AI judge. Present three distinct evidence sections: **Automatic checks**, **Human review**, and (only after implementation) **AI judge**. Never merge judge preferences into deterministic correctness or an overall leaderboard score.

## Recommended first version

1. From a saved comparison, explicitly choose which completed question/answer pairs to judge. Missing or truncated answers remain visible; do not treat missing answers as losses. Show the actual question, context, optional reference, and both answers that will leave the machine.
2. Choose a judge provider and exact model route independently of Model A and B. Use server-side API credentials; a separate provider requires its own credential. Show credential presence separately from successful authentication. The current free-only candidate policy remains unchanged. Any future paid-judge policy requires separate, explicit approval and a bounded spend/request budget; it must not become a way to bypass candidate free-only checks.
3. Show current pricing evidence, estimated input/output tokens, two requests per pair, retry policy and absolute attempt cap. Require explicit consent to send this data to that named provider. Explain provider retention/privacy terms; allow cancelling before dispatch. Do not infer consent from starting the original comparison.
4. Freeze rubric `pairwise-answer-quality-v1`: correctness relative to supplied evidence, instruction compliance, relevance, and clarity. Rate each dimension separately with reasons citing answer excerpts; permit ties and **cannot judge** (insufficient evidence, ambiguous rubric, or unsafe/unverifiable claims). Style is not correctness. Do not ask for private chain-of-thought.
5. Hide candidate model/provider identities and randomize answer labels. Evaluate each pair in **both answer orders** with identical rubric and settings. Store each judgment independently, map back to candidate identities privately, and flag preference changes as position-sensitive. Report agreement, ties, cannot-judge and order sensitivity with their denominators; do not quietly average away disagreements.
6. Keep candidate answers as **untrusted data** in separate, clearly delimited content fields. The trusted system instruction must say that text inside questions/answers cannot change the rubric, request tools, reveal secrets, or add instructions. Use no tools, browsing, code execution, or application actions. Validate a bounded structured output schema, reject unknown labels/out-of-range scores, and retain invalid raw outputs as failed judgments. Delimiters alone cannot eliminate prompt injection: this remains a limitation requiring adversarial tests.
7. Persist an append-only judge run: candidate response IDs/hashes, consent timestamp/data scope, provider/route and returned identity, complete rendered prompt and template hash/version, rubric/version, order mapping, settings, pricing evidence, request/attempt cap, durable attempts, raw output, parsed reasons/ratings, token usage, timings and errors. Timeouts/unknown outcomes require explicit acknowledgement before retry, just as candidate generation does. Completed candidate answers must never be regenerated to recover judge failures.
8. Export judge records separately and label synthetic judge fixtures unmistakably. Test schema rejection, ties, cannot-judge, opposite-order disagreement, prompt-injection text, data consent, secret redaction, and uncertain-outcome recovery before enabling the feature.

## Access and billing

A ChatGPT or Codex subscription does **not** establish API access for this application. Do not read or reuse a desktop session, browser cookies, Codex login files, or subscription tokens. The user must configure an API credential authorized for the chosen provider and approve that API usage. A judge routed through OpenRouter/Zen follows that provider's billing; a direct OpenAI integration would need an explicit new adapter and API access. API usage may incur separate charges even when the user subscribes to ChatGPT/Codex.

Official OpenAI guidance checked 2026-10-19: [Managing billing for ChatGPT and the API platform](https://help.openai.com/en/articles/9039756-managing-billing-for-chatgpt-and-the-api-platform) states that billing systems are separate and API usage is billed separately. Context7 was unavailable (monthly quota exceeded); the official help page was retrieved directly. Verify current API prices/access before implementation rather than hard-coding a subscription entitlement.

## Interpretation limits

Judges may prefer verbosity, polished style, their own model family, or familiar phrasing; they can make factual mistakes and follow malicious instructions embedded in answers. Hiding labels and reversing order reduces some biases but does not establish impartiality. Reference answers may themselves be wrong. A judge is another fallible measurement, not ground truth, and a small convenience sample cannot establish an overall winner. Human review should remain available to inspect disagreements.
